# src/Ui 実装計画メモ

## 目的

`src/Ui` の今後の実装を、現状の責務分離とスケジュールを踏まえて段階的に進めるための計画をまとめる。

今回の優先順位は以下とする。

1. Editor統合
2. 登録型の導入
3. アニメーション基盤
4. テキスト最小導入
5. 丸角表現
6. Lib化

Lib化は将来見据えるが、直近は「動き」と「運用しやすさ」を優先する。

## 現状整理

現状の `src/Ui` は主に以下の構成になっている。

- `Canvas`
  - ランタイム更新
  - 描画
  - JSON Load/Save
  - ImGui Editor 表示
  - Action 登録と実行
- `Element`
  - Sprite 表示データ
  - Event 設定
  - ImGui Editor 表示
- `EventSystem`
  - ActionKey と関数の対応付け

現状の課題は以下。

- `Canvas` に責務が集まりすぎている
- `Element` も描画データと Editor 表示を同時に持っている
- UI ごとに Editor ウィンドウが増えやすく、管理負荷が上がる
- 今後 `SkillTree` や `Pause` のような UI が増えると一覧性が悪化する
- アニメーションやテキスト追加時に、どこへ責務を置くかが曖昧になりやすい

## 今回の判断方針

### 先に解決すること

- UI 数が増えても Editor が破綻しないこと
- `Element` に対して最小限のアニメーションを足せること
- テキストを最小コストで UI に載せられること

### 後回しにすること

- UI の本格 Lib 化
- 丸角のシェーダ実装
- アニメーションのキーフレーム Editor
- 完成度の高いテキストレイアウト

### 設計上の前提

- Debug では ImGui ベースの Editor を持っていてよい
- Release では Editor 部分を除外できればよい
- 直近は汎用化しすぎず、まず既存 `Canvas` / `Element` を活かして改善する

## Phase 1: Editor統合

### 目的

UI ごとの Editor を残しつつ、表示窓口を統合してウィンドウ数を抑える。

### 方針

- `UiManager` のような新クラスを追加する
- 初手では Editor 用の一覧管理に責務を絞る
- `Canvas` はコードで明示登録する
- 表示は 2 ウィンドウ構成にする

### UI構成

#### 1. UI一覧ウィンドウ

- デフォルト表示する
- 各 UI は `CollapsingHeader` で並べる
- 各ヘッダー内に最低限以下を置く
  - 選択
  - Editor詳細の開閉
  - Element総数
  - Save
  - Reload
- `JSONパス` は常時表示せず、必要なら Tooltip とする

#### 2. 選択中Canvasウィンドウ

- 選択された `Canvas` を 1 つだけ表示する
- デフォルトでは未選択で空にする
- 中身は既存の `Canvas::Editor()` を極力流用する
- ゲーム上の `SetActive` 切り替えはこの詳細側で扱う

### 状態管理

- `Canvas` が持っている Editor 表示状態は `UiManager` 側に寄せる
- 同時に開く詳細対象は 1 Canvas に限定する
- `Canvas::StandaloneDebug()` は縮小または廃止寄り

ただし、最終的には「カスタマイズなしでも扱える入口」は別途残す必要がある。

### 実装タスク

- `UiManager` クラス追加
- `Canvas` 登録 API 追加
- UI一覧描画
- 選択中 Canvas 描画
- `Canvas::Editor()` の流用整理
- `Canvas` 側の `editing_` 依存整理
- `StandaloneDebug()` の役割再整理

## Phase 2: 登録型の導入

### 目的

`SkillTree` や `Pause` を含む UI を、Editor で一覧管理しやすくする。

### 初期スコープ

この段階では、登録型を「Editor 一覧都合の薄い registry」に留める。

直近で持てばよい情報は以下。

- UI名
- 対象 `Canvas`
- Element 総数取得
- Save / Reload 呼び出し対象
- Editor の選択対象

### やらないこと

- UI 実行時ロジックの完全抽象化
- ゲーム側 UI 制御の全面統一
- `SkillTree` / `Pause` のランタイム振る舞いまで共通化

### 将来の拡張余地

- `UiManager` に `Canvas` の取得や選択状態管理を寄せる
- Editor 用 registry とランタイム用 registry を分ける
- UI 用メタ情報を拡張する

## Phase 3: アニメーション基盤

### 目的

UI の見た目に最低限の動きを入れ、今後の拡張先を決める。

### 初期仕様

- 固定スロットは `Show` / `Hide`
- `Show` と `Hide` は別定義
- 定義は各 `Element` の JSON に直接持たせる
- 初手は単純 Tween
- 将来キーフレームへ拡張できる構造を意識する

### 初期対象プロパティ

- `position`
- `opacity`

`color` は次段候補とする。

### 仕様メモ

- `opacity` は `color.w` に吸収せず、独立値として扱う案を優先する
- ただし演出系プロパティの肥大化は懸念があるため、将来は専用の見た目パラメータ構造へ切り出す余地を残す
- 補間は `ease-in/out` を最低限サポートする
- `loop` や `hover/click/execute` は将来拡張対象とする

### Editor対応

- 初手では Editor 対応しない
- JSON 手編集で進める
- 本格対応するなら、単純 Tween ではなくキーフレーム編集を前提にしたい

### 実装タスク

- `Element` 用アニメーション定義構造追加
- JSON Load/Save 対応
- `Show` / `Hide` の再生条件整理
- Tween 再生器の追加
- `position` / `opacity` 適用処理追加
- easing の最小セット選定

## Phase 4: テキスト最小導入

### 目的

`Pause` や `SkillTree` の固定ラベルを最小コストで描画可能にする。

### 今フェーズで必要な機能

- 1行描画
- 位置指定
- 色指定
- スケール指定

### 今フェーズで不要な機能

- テキストボックス幅に応じた自動折り返し
- 高機能レイアウト
- 本格的な装飾

### 方針

- 外部ライブラリは使ってよい
- ただし「理解して統合した」と説明できることを重視する
- 将来差し替えやすい構造にする
- `Element` に text を混ぜるか、別型に分けるかは保留とする

### 実装方針の候補

#### 案A: フォントラスタライズだけ借りて描画は自前

- メリット
  - 統合方針を自分で説明しやすい
  - 差し替えしやすい
  - UI 描画系との整合を取りやすい
- デメリット
  - 初期実装コストは上がる
  - 文字配置やアトラス管理の最低限実装が必要

#### 案B: 描画まで含めて軽量な仕組みを借りる

- メリット
  - 最短で表示に到達しやすい
  - スケジュールに強い
- デメリット
  - 自作アピールは弱くなりやすい
  - UI システムとの責務境界が曖昧になりやすい

### ライブラリ候補比較

| 候補 | 使い方の方向 | メリット | 注意点 | 今回との相性 |
|------|--------------|----------|--------|--------------|
| `stb_truetype` | グリフ生成を借りる | 軽量、理解しやすい、統合を説明しやすい | レイアウトやアトラス管理は自前 | 高い |
| `FreeType` | フォント処理を借りる | 実績が高い、機能が豊富 | 依存としては重め、最小導入にはやや過剰 | 中 |
| `DirectWrite` | Windows API ベースで描画補助 | Windows 環境との親和性が高い | API 依存が強く、将来の抽象化に工夫が必要 | 中 |
| `ImGui` の文字描画流用 | Debug 用の簡易利用 | すぐ試せる | ランタイム UI の本命にはしづらい | 低 |

### 現時点の推奨

第一候補は `stb_truetype` か同等の軽量構成。

理由は以下。

- 最小導入に向いている
- 自前の描画統合に寄せやすい
- 「全部ライブラリ任せ」になりにくい
- 将来の差し替え余地を残しやすい

## Phase 5: 丸角表現

### 今回の扱い

後回し。

### 当面の方針

- テクスチャで回避する
- 必要なら Panel 系の見た目で先に吸収する

### 将来検討

- Sprite 拡張で丸角クリップ
- UI 専用矩形描画の追加
- 枠線や塗りを持つ Panel への発展

## Phase 6: Lib化

### 今回の扱い

実装優先度は低い。

### ただし意識すること

- ランタイムと Editor の責務は徐々に分ける
- JSON I/O と表示制御の境界を明確にする
- `UiManager` は将来 Lib 化しやすい単位を意識して設計する

Lib 化は、Editor 統合とアニメーション基盤の整理後に着手する方が安全。

## 補足

今回の計画では、まず「Editor で扱いやすいこと」を優先する。

`src/Ui` は今後も機能追加が続く想定のため、先に Editor を整理してからアニメーションとテキストへ進む方が、結果的に試行速度と設計の見通しが良い。
