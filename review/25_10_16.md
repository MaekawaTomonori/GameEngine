# DirectX12ゲームエンジン コードレビュー

**レビュアー視点**: Linus Torvalds
**レビュー日**: 2025-10-16
**対象**: PortfolioGame Engine (C++20 DirectX12ベース)

---

## 📊 総合評価

**品味評分**: 🔴 **1/10 - 完全な垃圾 (Complete Garbage)**

このコードは「動く」かもしれないが、"good taste"から程遠い。DirectX12のラッパーを書こうとして、C++の複雑性に溺れている状態。

さらに深刻なのは、開発者の説明により**Singletonキャッシングが意図的な設計**だと判明したこと。これは単なる無知ではなく、**根本的な設計の誤解**を示している。「アクセスのためだけのポインタ」という概念は、C++のメモリ管理において存在しない危険な幻想だ。

---

## 🤔 思考前提 - Linusの三つの問い

1. **"これは本当の問題か、臆想か?"**
   → 実際に動くエンジンなので実用的。ただし過度設計の兆候あり。

2. **"もっとシンプルな方法はないか?"**
   → データ構造から見直すべき箇所が多数ある。

3. **"何を壊すか?"**
   → ポインタ管理が散在。いつでもクラッシュしうる。

## 🚨 致命的問題

### 1. ポインタ地獄 + Singletonキャッシング - 二重のグローバル変数

**場所**: `Engine/include/Framework.hpp:30-54` + `Engine/src/Framework/Framework.cpp:43-52`

```cpp
// Framework.hpp
class Framework {
    GameEngine::Config* config_ = nullptr;           // 生ポインタ
    std::unique_ptr<IGame> game_;                     // unique_ptr
    SceneSwitcher* scene_ = nullptr;                  // 生ポインタ
    std::unique_ptr<WinApp> windows_;                 // unique_ptr
    Input* input_ = nullptr;                          // Singletonキャッシュ
    TextureManager* texture_ = nullptr;               // Singletonキャッシュ
    SpriteCommon* sprite_ = nullptr;                  // Singletonキャッシュ
    ModelCommon* model_ = nullptr;                    // Singletonキャッシュ
};

// Framework.cpp
void Framework::Initialize() {
    input_ = Singleton<Input>::GetInstance();
    texture_ = Singleton<TextureManager>::GetInstance();
    sprite_ = Singleton<SpriteCommon>::GetInstance();
    model_ = Singleton<ModelCommon>::GetInstance();
    // なぜSingletonをキャッシュする？
}
```

**問題点**:

#### 🔴 **Critical: 二重のグローバル変数**
Singletonは既にグローバルアクセス可能なのに、なぜFrameworkでもキャッシュする？

これは**二重のグローバル変数システム**だ:
1. `Singleton<TextureManager>` - 第一のグローバルアクセスポイント
2. `Framework::texture_` - 第二のグローバルアクセスポイント

**何も解決していない。複雑性を2倍にしただけだ。**

#### 🔴 **Critical: ダングリングポインタの温床**
```cpp
// Frameworkの寿命中にこれが起きる可能性:
SingletonFinalizer::Finalize();  // Singletonを破棄

// Framework::texture_ は今、ダングリングポインタ！
// しかしFrameworkはそれを知らない
// 次のアクセスでクラッシュ
```

**誰が先に破棄されるか保証できない。** これは時限爆弾だ。

#### 🔴 **Critical: "非所有ポインタ"という幻想**
開発者の意図: _"所有ではなくただアクセスするためのポインタ"_

**C++にそのような概念は存在しない。** ポインタは以下のいずれかだ:
1. **所有ポインタ** (`unique_ptr`, `shared_ptr`) - 削除責任あり
2. **観察ポインタ** (`T*` from `unique_ptr::get()`) - **寿命保証なし**
3. **参照** (`T&`) - 生存保証あり（nullptrにならない）

現在のコードは「観察ポインタ」だが、**寿命保証がゼロ**。

**原則違反**:
> "Bad programmers worry about the code. Good programmers worry about data structures and their relationships."

**修正案 - Option A: Frameworkが所有（推奨）**
```cpp
class Framework {
    // すべてFrameworkが所有
    std::unique_ptr<Input> input_;
    std::unique_ptr<TextureManager> texture_;
    std::unique_ptr<SpriteCommon> sprite_;

public:
    Framework()
        : input_(std::make_unique<Input>())
        , texture_(std::make_unique<TextureManager>(...))
        , sprite_(std::make_unique<SpriteCommon>(...))
    {}

    // 他のクラスに渡す時は参照で
    Input& GetInput() { return *input_; }
    TextureManager& GetTextureManager() { return *texture_; }
};
```

**利点**: 所有権明確、寿命明確、テスト可能、ダングリングポインタ不可能

**修正案 - Option B: Singletonを使うなら直接使え（非推奨だが一貫性はある）**
```cpp
class Framework {
    // ポインタキャッシュを完全削除
};

void Framework::Update() {
    Singleton<Input>::GetInstance()->Update();  // 必要な時に直接アクセス
    Singleton<TextureManager>::GetInstance()->Draw();
}
```

**利点**: 少なくとも一貫性がある、ダングリングポインタリスク減少

**修正案 - Option C: 参照で保持（中間案）**
```cpp
class Framework {
    Input& input_;
    TextureManager& texture_;

public:
    Framework()
        : input_(*Singleton<Input>::GetInstance())
        , texture_(*Singleton<TextureManager>::GetInstance())
    {}
};
```

**利点**: nullptrチェック不要、所有しないことが明確

#### 📊 設計決定の比較

| アプローチ | 所有権 | 寿命保証 | テスト可能性 | 安全性 | 推奨度 |
|----------|--------|---------|------------|--------|--------|
| **現在（Singleton+キャッシュ）** | ❌ 不明確 | ❌ なし | ❌ 不可能 | 🔴 危険 | **0/10** |
| **Option A（Frameworkが所有）** | ✅ 明確 | ✅ あり | ✅ 可能 | 🟢 安全 | **10/10** |
| **Option B（直接Singleton）** | ⚠️ グローバル | ⚠️ 微妙 | ❌ 困難 | 🟡 中 | **3/10** |
| **Option C（参照で保持）** | ⚠️ 外部 | ⚠️ 依存 | ⚠️ 微妙 | 🟡 中 | **5/10** |

### 2. Singletonの濫用 - グローバル変数の言い訳

**場所**: `Engine/include/Pattern/Singleton.hpp`

```cpp
template <typename T>
class Singleton {
    static T* instance_;
    static void Create() {
        instance_ = new T();  // 生new!
    }
};
```

**問題点**:
- Singletonはグローバル変数に花を持たせただけ
- テストが不可能（モックできない）
- マルチスレッド環境での拡張性ゼロ
- なぜ`TextureManager`がシングルトンである必要がある？

**評価**:
> "Singletonは90%のケースで間違った選択だ。"

**修正案** - 依存性注入を使用:
```cpp
class TextureManager {
    DirectXAdapter& adapter_;
    SRVManager& srv_;

public:
    TextureManager(DirectXAdapter& adapter, SRVManager& srv)
        : adapter_(adapter), srv_(srv) {}
};
```

### 3. Matrix4x4::Inverse() - 110行の悪夢

**場所**: `Engine/include/Math/Matrix.hpp:109-143`

```cpp
Matrix4x4 Inverse() const {
    float a = matrix[0][0] * matrix[1][1] * matrix[2][2] * matrix[3][3] +
              matrix[0][0] * matrix[1][2] * matrix[2][3] * matrix[3][1] +
              matrix[0][0] * matrix[1][3] * matrix[2][1] * matrix[3][2] -
              // ... 100行以上続く巨大な単一式
```

**問題点**:
- **110行の単一式計算**は人間が読めない
- コンパイラが最適化できない（複雑すぎる）
- デバッグ不可能
- 保守不可能

**原則違反**:
> "If you need more than 3 levels of indentation, you're screwed."

**修正案**:
```cpp
Matrix4x4 Inverse() const {
    const float det = Determinant();
    if (std::abs(det) < 1e-8f) return Identity();

    Matrix4x4 adj = Adjugate();  // 補助関数に分解
    return adj * (1.0f / det);
}

// 各ステップを分離
float Determinant() const {
    // 小さな関数に分解
}

Matrix4x4 Adjugate() const {
    // 小さな関数に分解
}
```

### 4. SRVManager::Allocate() - バウンドチェックのタイミングがおかしい

**場所**: `Engine/src/DirectX/Heap/SRVManager.cpp:33-41`

```cpp
uint32_t SRVManager::Allocate() {
    assert(useIndex_ <= kMaxSRVCount);  // これは遅すぎる

    uint32_t index = useIndex_;
    ++useIndex_;
    return index;
}
```

**問題点**:
- `useIndex_ == kMaxSRVCount`の時、インクリメント後に範囲外になる
- assertが意味をなしていない

**修正案**:
```cpp
uint32_t Allocate() {
    assert(useIndex_ < kMaxSRVCount);  // インクリメント前にチェック
    return useIndex_++;
}
```

**さらに深刻な問題**:
- なぜ固定サイズ512なのか？根拠は？
- 動的に拡張できないのか？
- マジックナンバーの濫用

### 5. LevelEditor::Spawn() - 例外安全性ゼロ

**場所**: `Engine/src/Stage/LevelEditor.cpp:46-66`

```cpp
void LevelEditor::Spawn() {
    std::vector<StageObject> newObjects;
    for (auto& object : data->objects) {
        StageObject stageObject;
        stageObject.model = std::make_unique<Model>();  // 例外が投げられたら？
        stageObject.model->Initialize(object.file);      // ここで失敗したら？
        newObjects.push_back(std::move(stageObject));
    }
    objects_ = std::move(newObjects);
}
```

**問題点**:
- `Initialize()`が失敗したら、`newObjects`は部分的に初期化された状態で放置
- メモリリーク予備軍
- エラーハンドリングが完全に欠如

**修正案** - トランザクション的アプローチ:
```cpp
void Spawn() {
    std::vector<StageObject> newObjects;
    newObjects.reserve(data->objects.size());  // 再割り当て回避

    try {
        for (auto& object : data->objects) {
            newObjects.push_back(CreateObject(object));
        }
        objects_ = std::move(newObjects);  // 成功時のみコミット
    } catch (...) {
        // newObjectsは自動的に破棄される
        throw;
    }
}
```

### 6. TextureManager - 不必要なmutex

**場所**: `Engine/src/Texture/TextureManager.hpp:39`

```cpp
std::mutex mutex_;
```

**問題点**:
- なぜテクスチャマネージャーがマルチスレッド対応している？
- ゲームループは基本的にシングルスレッドのはず
- Mutexは「ここに設計問題がある」という赤旗

**分析**:
- ロードがバックグラウンドスレッド？ → ロード専用キューを使うべき
- メインスレッドのみ？ → mutexは不要

**評価**:
> "Mutexは問題を解決していない。問題を隠蔽しているだけだ。"

### 7. IScene::Setup() - ヘッダー汚染

**場所**: `Engine/include/IScene.hpp:67`

```cpp
void Setup(SceneSwitcher* _switcher, PostProcessExecutor* _ppe, DebugUI* _debug) {
    switcher_ = _switcher;
    postEffects_ = _ppe;
    debug_ = _debug;
}
```

**問題点**:
- なぜこれがヘッダーにインラインで書かれている？
- バイナリ互換性を壊す
- コンパイル時間が増大
- 引数が多すぎる（3つ以上は構造体にまとめるべき）

**修正案**:
```cpp
// ヘッダー
struct SceneContext {
    SceneSwitcher* switcher;
    PostProcessExecutor* postEffects;
    DebugUI* debug;
};

void Setup(const SceneContext& context);

// .cpp
void Setup(const SceneContext& context) {
    switcher_ = context.switcher;
    postEffects_ = context.postEffects;
    debug_ = context.debug;
}
```

## 💡 改善の方向

### 1. データ構造を修正 - 所有権を明確に

**現在の問題**:
```
Framework → TextureManager* (誰の所有?)
         → Input* (誰の所有?)
         → Scene* (誰の所有?)
```

**あるべき姿**:
```
Framework owns {
    DirectXAdapter
    ResourceManager owns {
        TextureCache
        ModelCache
    }
    InputSystem
    SceneGraph owns Scenes
}
```

### 2. Singletonを削除 - 依存性注入に置き換え

すべてのシングルトンを通常のクラスに変換し、コンストラクタインジェクションで依存性を渡す。

### 3. エラーハンドリングを一貫させる

**現在は混在**:
- `assert()` (デバッグのみ)
- `Log::Send()` (ログのみ)
- 例外なし
- 戻り値チェックなし

**一貫したポリシーを選択**:
- 回復可能: `std::optional<T>`または`Result<T, Error>`
- 回復不可能: `std::terminate()`
- 例外は使わない（ゲームエンジンでは遅すぎる）

### 4. 複雑度を下げる

**ルール**: 3層ネスト以上は関数分割

対象:
- `LevelEditor::Spawn()`
- `Matrix4x4::Inverse()`
- 巨大な初期化関数群

## 🎯 結論

> "Bad programmers worry about the code. Good programmers worry about data structures and their relationships."

**このコードは動くが、保守不可能だ。**

### 最も深刻な問題
開発者の説明により、**Singletonキャッシングパターン**が意図的な設計だと判明した:
> _"Singletonで扱っている値達はアクセスを返すため生ポインタを使っています。所有ではなくただアクセスするためのポインタという認識です。"_

**これは問題を理解していない証拠だ。**

なぜFrameworkがSingletonへのショートカットを保持する必要がある？これは:
1. **二重のグローバル変数** - 複雑性を2倍にするだけ
2. **ダングリングポインタの温床** - 破棄順序を制御できない
3. **"非所有ポインタ"という幻想** - C++にそのような安全な概念は存在しない

どちらか一方にしろ:
- **推奨**: Frameworkが所有する（依存性注入）
- **非推奨**: Singletonを直接使う

**両方やるのは最悪だ。**

データ構造から見直せ。所有権を明確にし、Singletonキャッシングを削除し、エラーハンドリングを一貫させろ。そうすれば、コードは自然にシンプルになる。

**最終評価**: 2/10 → **1/10** - 意図的な悪設計とわかり、評価を下げる。
